Plain-English Guide

What CUDA, llama.cpp, and LoRA actually do.

If you have never trained a local AI model before, here is the exact mental model behind how Hermione's assistant went from a generic 47% base model to a 92.6% specialist running on a MacBook.

What is CUDA? Is it on my Mac?

CUDA is NVIDIA's math engine that lets AI training run thousands of calculations in parallel on an NVIDIA GPU instead of one-by-one on a CPU. Macs do not have CUDA — Apple Silicon chips (M1–M4) use Apple's Metal instead. So we rent NVIDIA GPUs on Runpod (CUDA) for the heavy training, then export a single file that runs fast on your Mac (Metal).

What are llama.cpp and .gguf?

llama.cpp is a lightweight C++ runtime that executes AI models directly on a laptop without Python or cloud servers. .gguf is the compressed single-file format it reads — like an MP3 for AI weights. 4-bit quantization (Q4_K_M) shrinks a ~4 GB model to 1.32 GB so it runs smoothly on an 8 GB Mac.

How does LoRA fine-tuning work?

Instead of retraining all 2.23 billion weights from scratch, LoRA attaches a tiny trainable layer (21.8M parameters — under 1% of the model). We show it 28,800 synthetic Hermione requests paired with exact tool calls, nudge only those weights until validation loss drops from 0.228 to 0.0056, then merge them permanently into the model.

Why not just call ChatGPT or Claude?

Privacy & zero per-message cost. Your issues, roadmap, and notes stay in one file on your machine and never hit a cloud API. A tiny 2B model specialized for Hermione's exact 21-tool schema responds in milliseconds and costs $0 to run forever.

Why hermione-2b & 2b-web excelled

hermione-2b hit 100% accuracy on 14 of 26 categories (navigation, moves, priority, points, assignment, pages, drafts, comments, themes, archiving, and mid-thread corrections). hermione-2b-web hit 100% on 12 categories while citing source hostnames on multi-step web research.

Why hermione-4b was blocked at 74.8%

On 23% of test requests, Qwen3-4B-Instruct-2507 emitted literal </tool_call>\n\n</tool_call> tags without parsed calls — a Jinja chat-template / stop-token mismatch rather than a data problem (since both 2B models hit >91% on the exact same dataset). The release gate did its job and blocked publication.

6 Live-Pod Bugs Caught & Fixed

1. Pre-loop llama-server build order (--setup-only) + missing base.json guard.
2. Linux sha256sum fallback + HfApi().upload_file() replacing deprecated CLI.
3. Ubuntu 24.04 PEP 668 PIP_BREAK_SYSTEM_PACKAGES=1 + zipfile +x bits.
4. Stopped llama.cpp reqs from overwriting CUDA PyTorch with torch+cpu & added /usr/local/cuda/bin to PATH.
5. Unwrapped Qwen3VLProcessor & rendered templates before Dataset.from_list to stop PyArrow null-key schema bloat past 4,096 tokens.
6. Fixed post-CUDA datasets.map(num_proc=8) fork deadlock on 26-vCPU H100 with num_proc=1.

Offline Ed25519 Manifest Verification

The signing key (~/.hermione-license/private.pem) never touches a cloud pod. scripts/license.mjs sign-manifest signs models.src.json on the Mac and attaches models.json to GitHub Release v0.2.0. Hermione verifies both the Ed25519 signature and the exact SHA-256 digest before loading any .gguf.
